# Fastauth v0.15.0 implementation plan

**Goal:** Ship the approved typed server contract release with its prerequisite correctness fixes.

**Architecture:** Preserve the existing flow/adapter/plugin layering. Add atomic storage capabilities rather than unsafe fallbacks, a policy boundary around session issuance/read/refresh, typed namespaces around existing flows, and bounded off-loop password execution. Retain stateless JWT access-token expiry semantics while making refresh identity and revocation coherent.

**Scope:** The next-version assessment approved on 2026-10-02. OAuth/OIDC, MFA, passkeys and organizations are deferred.

## Constraints

- Python >=3.11; Pydantic models for new data contracts; strict Pyright and existing 80% coverage gate
- No silent unsafe adapter fallback; explicit migration for adapter capabilities, JWT identifiers, indexes, new status/timestamp fields and dependency floors
- Existing user metadata remains application data, not trusted claims
- Legacy users default active; legacy authentication timestamps remain unknown, never artificially fresh
- Required production database tests must execute, not silently skip
- No credentials/security-setting changes; publish through existing trusted release workflow only after review and checks

## Tasks

1. Storage invariants: regressions for rejected signup, failed/cancelled account creation and retry; typed atomic challenge consume/attempt and replacement semantics for Memory/Mongo/Postgres; nullable username migration and actual persistent-adapter tests
2. Session invariants: stable signed JWT logical session IDs; refresh/logout/revoke-other parity; atomic Mongo family revocation; shared-worker key convergence, ongoing rotation and retirement grace; preserve original authentication time on renewal
3. Typed extension contracts: OTP, verification, JWT and audit services; omitted/null patch parity; enforce endpoint protection and server-only mounting; complete mutation hooks; reusable custom-handler limiter; accurate OpenAPI schemes, errors and operation IDs
4. Account policy: privileged active state, verified-session policy, authenticated actor helpers and recent-auth dependencies; optional application policy callback for session/API-key operations; explicit audited trusted status mutations
5. Async passwords: bounded off-loop execution with cancellation-safe concurrency accounting; retain injected synchronous hasher compatibility; rehash only following successful verification
6. Delivery contract: migration/production deployment/email recipes, corrected docs claims, executable examples, tested dependency floor/latest and independent wheel extras
7. Release gates: integrate; lint/type/unit/integration/coverage/build/Twine/docs; independent whole-branch review; hosted persistent database matrix with no required skips; immutable checked commit, merge and trusted tag release; verify GitHub/PyPI artifact and clean install

Each implementation task starts with failing regressions, then minimal changes, covering tests and a conventional commit. Review follows integration, and later edits rerun affected and aggregate checks.

## Review focus

- Cancellation after writes must not strand an identity or lose a password-work concurrency slot
- Refresh must preserve legacy unknown authentication time and never revive suspended accounts
- Concurrent challenge consume/attempt and family revoke/rotate must have deterministic, persistent-store outcomes
- Old workers and old signing secrets must not mint unverifiable tokens through rotation
- SDK trusted principals remain distinct from authenticated actors; null patch intent and plugin policy metadata must match real HTTP behavior
